Executive Summary

What TeamFrame is

TeamFrame is a lightweight HR structure tool for startups with 6–25 employees. It is described as a "check-engine light for founder people-ops risk." Core features: employee directory, onboarding task tracking, leave management, document expiry monitoring. It is not payroll, not an HR platform, and not an AI advisor. Those are explicitly out of scope.

Overall Repository Health

Moderate risk — not yet production-ready. The product works end-to-end and passes all 13 tests, but the database security layer has multiple open gaps (missing RLS policies on key tables), the authentication callback flow has a known regression risk, and important security headers are absent. None of these are show-stoppers for continued development, but all must be resolved before real users interact with the system.

Key Risks

  • Auth callback regression (CRITICAL): The auth callback route was replaced with a shorter version during the pivot. The previous hardened version was removed. Any user who clicks an expired or already-used magic link could lose their existing session.
  • Missing RLS on companies and onboarding_tasks (CRITICAL): These tables have no RLS policies, meaning cross-tenant reads are possible via direct Supabase REST access.
  • No security headers (CRITICAL): The app is vulnerable to clickjacking, MIME sniffing, and cross-site scripting without CSP, X-Frame-Options, and related headers.
  • No rate limiting on magic link (HIGH): The email magic link endpoint has no throttle. An attacker could enumerate user accounts or spam users with magic link emails.
  • No logout route (HIGH): There is no logout mechanism in the app. Users cannot sign out. This is both a UX gap and a security gap.

Missing Functionality

  • Logout — no route or server action exists for signing out
  • Document upload UI — the service layer is wired but the upload interface is not shipped
  • Org chart hierarchy — B1 is blocked (manager_id data exists but rendering is not built)
  • Sentry DSN — error monitoring is wired but dormant

Incomplete Functionality

  • A6 (Middleware coverage) — code appears complete but issue tracker not updated
  • Document expiry signal engine — wired; document upload UI in progress

Module: Database Security (RLS & Schema)

IDIssuePlain DescriptionBusiness ImpactTechnical ImpactSeverityEvidenceRecommended ResolutionStatus
DB-01 Companies table has no tenant isolation The companies table (which holds each customer's data) has no row-level security policy. Any authenticated user could read or modify another company's record via the Supabase REST API. A customer could see or alter another customer's company name, settings, or tenant ID. This is a data breach risk. RLS enabled but zero policies on companies table means all rows are accessible to authenticated users via service role bypass. Critical schemas/companies.sql, schemas/tenancy_rls.sql, docs/launch/audit-findings-consolidated.md (M1) Add tenant isolation RLS policy to companies table: SELECT and UPDATE restricted to rows where tenant_id matches current_actor_tenant_id(). Open
DB-02 Onboarding tasks table has no access policies The onboarding tasks table has row-level security switched on, but no actual rules have been written. This means nobody can access it — including the app itself — which will cause silent failures. Onboarding tasks may silently fail to load or save for all users. Admin and employee workflows are at risk. RLS enabled with zero policies = all queries return empty or are rejected. App reads will silently return no rows without error. Critical schemas/onboarding_tasks.sql, schemas/tenancy_rls.sql, audit-findings-consolidated.md (M2) Add RLS policies to onboarding_tasks: tenant-scoped SELECT for admin + own record for employee; INSERT/UPDATE/DELETE restricted to admin. Open
DB-03 Employee records return too much information When an employee views the company directory, they can currently see all fields including private details. The database should restrict what non-admin users can see to only safe public information (name, role, department). Employees could access each other's personal information, timezone, employment type, and other fields they should not see. No employees_public view or column-scoped RLS policy exists. Employee SELECT RLS returns full row to tenant scope. Critical schemas/employees.sql, schemas/tenancy_rls.sql, docs/rbac-rules.md (org chart whitelist), audit-findings-consolidated.md (M7) Create employees_public view restricted to org chart fields (id, full_name, role_title, department, manager_id, status). Add employee-scope RLS that reads from this view only. Open
DB-04 Invite process can overwrite another company's employee metadata When an admin invites a new employee, the system updates that person's Supabase account metadata. If the person has an existing account at another company, this could overwrite their existing company assignment. An employee's link to their actual employer could be silently replaced, locking them out of their real account and leaking their data to a different company. inviteEmployeeAuthUser in employeeService does not check whether target auth user's app_metadata.tenant_id already belongs to a different tenant before overwriting. Critical services/employeeService/index.ts, audit-findings-consolidated.md (M5) Before updating app_metadata, check if the existing tenant_id in app_metadata belongs to a different tenant. If so, block the invite with EMPLOYEE_INVITE_TENANT_CONFLICT. Open
DB-05 Policies and procedures visible to all authenticated users Company policies and procedures should only be visible after they have been officially published. The current database rules may allow unpublished drafts to be read by all employees. Employees could read draft policy documents that were not intended for them, including confidential HR policies in preparation. No is_published filter on RLS SELECT policy for policies and procedures tables for non-admin roles. High schemas/policies.sql, schemas/procedures.sql, schemas/tenancy_rls.sql, audit-findings-consolidated.md (M13) Add RLS condition: employee-role SELECT restricted to rows where is_published = true. Verify is_published column exists in schema first. Open
DB-06 Tenant identity resolution can return the wrong company The system identifies which company a user belongs to by matching their email address. If a user's email appears in more than one company, the system may return the wrong company without warning. A user could end up in the wrong company's account, seeing another company's employees, leaves, and documents. current_actor_tenant_id() email fallback has no ORDER BY + LIMIT 1 — non-deterministic when a user email matches multiple tenant rows. High schemas/tenancy_rls.sql, audit-findings-consolidated.md (M14) Add ORDER BY created_at LIMIT 1 to the email-fallback CTE in current_actor_tenant_id(). This is a one-line SQL change. Open

IDIssuePlain DescriptionBusiness ImpactTechnical ImpactSeverityEvidenceRecommended ResolutionStatus
AUTH-01 Clicking a stale magic link could sign you out When a user clicks an expired or already-used magic link, the app currently risks clearing their active session cookies. A signed-in user who accidentally clicks an old link could be logged out unexpectedly. Users are unexpectedly signed out. This is especially damaging if an admin is mid-task. Customers will complain. app/auth/callback/route.ts was replaced with a shorter implementation during the pivot; the previous hardened callback that preserved session on stale links was removed. Repo cleanup audit flags this as "highest architecture/behavior inconsistency." Critical app/auth/callback/route.ts, docs/audits/repo-cleanup-audit-2026-05-31.md (Risk Register #1), audit-findings-consolidated.md (M8) Restore the hardened callback behavior: on stale/invalid link, attempt session recovery first; only redirect to error page if no session exists; never wipe PKCE verifier cookies that belong to active sessions. Open
AUTH-02 No way to sign out There is no sign-out button or logout action anywhere in the app. Once signed in, a user stays signed in permanently (or until the session expires). Users cannot securely end their session. On shared computers, this is a data security risk. All users will notice this eventually. app/auth/logout/route.ts does not exist. No server action for sign-out was found. The nav in app/layout.tsx has no logout link. High app/auth/ (directory listing), app/layout.tsx, audit-findings-consolidated.md (M15) Create a server action for sign-out (POST method only for CSRF protection) that calls supabase.auth.signOut() and redirects to /auth. Add a sign-out button to the navigation. Open
AUTH-03 Magic link email has no rate limit Anyone can request a magic link email for any address as many times as they want. This could be used to flood a user's inbox or to check whether an email address is registered in the system. Users could receive spam from the app. Malicious actors could discover which email addresses are registered. This could also overload the email sending service. sendMagicLink server action (app/auth/actions.ts) has no rate-limit check. No IP or email throttle is applied before calling supabase.auth.signInWithOtp(). High app/auth/actions.ts, audit-findings-consolidated.md (M16) Add server-side rate limiting: maximum 5 requests per IP per 15 minutes and 3 requests per email address per 10 minutes. Use an in-memory or Redis-backed store appropriate to the deployment environment. Open
AUTH-04 Employee account setup can fail partway through When an admin creates a new employee, two things must happen: a record is saved in the database, and an invite email is sent. If the email step fails, the employee record exists but is in a broken state with no way for the admin to see it clearly or fix it. Employees may never receive their invite. Admins have no clear indicator that provisioning failed. Employees are stuck unable to log in. inviteEmployeeAuthUser and employee record creation are not wrapped in a transaction. Partial failure leaves the employee row in a non-activated state with no admin-visible recovery path. High services/employeeService/index.ts, audit-findings-consolidated.md (M9) Either make provisioning atomic (wrap in a DB transaction) OR add a clear link-status field visible to admins on the employee record, plus a manual re-invite action with clear error messaging. Open

SEC-01 No security headers on web responses Every page the app serves is missing important security instructions that tell browsers how to behave safely. Without these, the app is more vulnerable to common web attacks like embedding the app in a hidden iframe (clickjacking), loading malicious scripts, or sniffing file types. A malicious website could embed TeamFrame in a hidden frame and trick users into performing actions without realising it. Sensitive data could be leaked via insecure browser behavior. next.config.ts has no headers() function. Missing: Content-Security-Policy, Strict-Transport-Security, X-Frame-Options, X-Content-Type-Options, Referrer-Policy. OWASP Top 10 item A05 (Security Misconfiguration). Critical next.config.ts, audit-findings-consolidated.md (M3) Add a headers() function to next.config.ts that sets all five headers. CSP should start with a strict policy (default-src 'self') and be relaxed only as needed for Supabase and Sentry domains. Open
